## 1. 先说清楚：我们不是从零开始

我们已经确定参赛赛道，也谈过真实数据、联网模型、Agent、MCP、不同数据类型、可视化、持续追问、证据、PDF、多模型接入和公网交付。现在需要纠正的是**决策级别和主次**，不是抹掉已有讨论或要求重新从三个产品口号中投票。

当前最稳妥的一句话工作假设：**面向真实数据、由 Agent 驱动的跨类型分析与可视化网页；让用户看见不同数据产生不同的调查方式和合适的结果表达。**这句话描述待验证的产品体验，不等于承诺任意文件自动准确分析；也尚不是最终营销口号。

## 2. 比赛约束：硬条件先于亮点

以下来自该赛项当前详情，下一步仍应以个人中心和组委会通知核对具体提交入口及有效时间。

### 2.1 资格与参赛边界

- 作品为原创 AI Web 应用，不是直接包装开源项目；AI 要是应用核心，而非只接一个 API。
- 团队 1—3 名同校学生，指导教师不超过 2 名；研究生/A/B/C 组别须按页面所列资格报名，错报组别页面称将取消资格。
- 前端 Web 是**主要呈现形态**；官网写明后端仅作为 AI 能力接入层、不是重点考察对象。其含义不是“禁止后端计算”，而是不能以复杂后台工程代替前端可见的 AI 产品体验。
- 作品涉及用户数据要做隐私保护；商用 AI API 费用由参赛方承担；可以用 AI 辅助编程，但团队成员要能解释实现。

### 2.2 提交硬件与时间风险

| 项目 | 页面要求或已发现的风险 | 对我们意味着什么 |
| --- | --- | --- |
| 代码仓库 | GitHub/Gitee 可评审；README、架构、运行说明、团队信息、依赖/环境变量模板、真实 Git 历史 | 开发过程和材料要可复现；公开仓库不能包含 API 密钥。 |

## 3. 评委怎么打分：映射到实际可见证据

赛项一级维度为：AI 技术深度 35%、创新性 25%、前端工程质量 10%、实用性 10%、用户体验 10%、社会价值与商业潜力 10%。这不是选取某个技术就自动得分的计分器。

| 考察点 | 官方细项/权重 | 数鉴必须展示的证据方向 | 当前是否已证实 |
| --- | --- | --- | --- |
| 模型集成 | AI 子项 8% | 数据分析专用 Prompt/结构化输出、模型适配与失败边界；不同真实任务下稳定性测试 | 未实现，未验证 |
| Agent/工作流 | AI 子项 8% | 问题理解→计划→真实工具结果→自主调整/澄清/停止；与固定流程的增量有实例 | 已确定要做；效果未验证 |
| RAG | AI 子项 6% | 若真实表格附带指标定义/财报附注/调查说明，检索出处能否改善口径回答 | 是否适用未验证；不能把 SQL 算成 RAG |
| 多模态 | AI 子项 5% | 若真实 PDF/扫描表能经视觉解析、人工核对并回指原页，才有可信应用价值 | 是否可做未验证；不能把文本 PDF 抽取算多模态 |
| 安全可控 | AI 子项 4% | 无证据不定论、错误口径澄清、工具与查询约束、敏感数据保护、失败透明 | 需求方向明确；未实现 |
| MCP/工具 | AI 子项 4% | Agent 调用真正的数据查询/统计工具，有脱敏、可核对的结果；不把普通函数调用称为 MCP | 真实工具调用保留；MCP 协议暂搁置，不作为首版前提 |
| 选题/方案/交互创新 | 创新 25% | 评委可操作地看见“不同数据→不同分析路径与可视化”，并能追问纠错 | 核心方向用户已选择；实现形式未验证 |
| 前端工程+体验 | 合计 20% | 主流程清楚、图表交互/状态反馈好、响应式与性能可信；技术日志不压过产品 | 尚无实机测试 |
| 实用性+社会/商业 | 合计 20% | 明确谁在用、解决何种真实任务；给出真实数据测试、成本与隐私边界 | 客群与价值需用户研究 |

**评分取舍**：RAG 与多模态共占 AI 子项 11 个百分点，是实际机会成本，既不能不评估就一概推后，也不能靠名词凑分；应尽快用一份有原始文档的真实数据验证“做出来会不会让答案更好”。如果有益但本批时间不足，要明确放弃范围和相应得分风险。

## 4. 对已有方案的纠偏：保留、待定、撤回

| 旧版 PRD/讨论中的表述 | 当前处理 | 原因与下一步判定 |
| --- | --- | --- |
| 「挑战这条结论」是**主创新交互** | **撤回主角地位，保留可信分析能力候选** | 用户选的第一印象是跨类型分析；只有证明挑战显著强化演示才提升权重。 |
| Agent 是“实现手段”或“所有步骤都由 AI 完成” | **都不准确** | Agent 的计划/工具观察/调整应可见；解析、数值计算与审计仍应有确定性代码，分工待真实案例验证。 |
| 独立公网 MCP Server、固定必须三个工具 | **首版搁置 MCP；撤回固定数量要求** | Agent 仍需使用真实分析工具；协议是否以后引入再看收益与成本。未实现 MCP 就不能宣称使用 MCP。 |
| 必须有两套联网模型作为首版阻断条件 | **待定，原 PRD 中的 P0 过早** | 用户要求多款 API 兼容方向；首版要证明多少款、访客是否能选、是否 BYOK，要看评委价值/费用/稳定性后确定。 |
| 财务表+问卷表是首版**指定必测数据** | **作为优先验证样例，不是用户最终选定的业务定位** | 关键不是凑两份文件，而是异质字段让 Agent 真的改变分析；样本需授权/可核验。 |
| 五类图表首版全部支持 | **待验收任务定范围** | 图表要适用于数据且正确；强行五种可能减分，不把数量等于质量。 |
| PDF 多模态/RAG 自动定 P1 | **改为尽早做可行性判定，不先承诺 P0/P1** | 官网有对应细项；只有真实文档与可验证收益才立项，不牺牲主闭环。 |
| `sql.js`、Fastify、服务端 HTML 报告、SSE、特定部署方式 | **实现候选，不是产品方向本身** | 依据评委体验、真实数据、隐私/安全、预算和公网可运维性选择。 |
| “一条命令本地启动”当作品目标 | **保留复现要求，不代替公网目标** | 用户已确认评委应能独立打开公网作品。 |

**关键原则**：MCP 暂不纳入首版承诺，不能把一般工具调用包装成 MCP；模型名称切换不等于跨类型分析能力；给原始行位置不等于自动证明聚合结论。每个亮点都要有可演示、可复核的用户收益。

## 5. 暂定产品策略：赛规优先，承接用户想法

这不是最终 PRD，而是目前最一致的**参赛工作假设**：

> **数鉴 Agent：给真实表格一个懂数据语义、会规划调查且能随问题追问的 AI 分析工作台。面对不同类型数据，先理解字段和口径，再以实际计算生成相应图表及可核查解释。**

### 5.1 评委可见的演示主线（不是预制答案脚本）

1. **同一网页、两份真实且有出处/授权、结构差异明显的数据**，观察字段/记录粒度识别和质量提醒是否不同。
2. 用户对第一份数据提出真实问题；Agent 给出需确认的口径、接下来的调查步骤，调用真实工具，图表逐步呈现；不能回答的条件直说。
3. 切换第二份数据：不是重复固定图表，而是**分析口径、计划、查询维度和图表选择发生符合数据语义的变化**。
4. 用户追问某个图或限定一组记录，真实重算；点击数值检查计算与数据版本。若挑战结论增强展示，可放在追问环节，不抢主线。
5. 如果有限 PDF/RAG 或多模型切换有实测增益，再加入材料和演示；不以未验证技术点占用整段演示。

这是对产品方向的**验证任务**，不是说现有网页已支持这些行为，更不预言现场一定输出理想答案。

### 5.2 怎么评估“真的会分析不同数据”

在真实数据（合法来源、明确字段口径）上测：能否识别数据粒度、日期与单位；是否询问影响答案的歧义；是否把样本内结果扩大为总体、把相关说成因果；生成的 SQL/统计是否复算一致；提问改变后是否实际重算；两个数据类型的调查计划是否存在**有理由的不同**而非换皮话术；模型失败或字段不支持时是否明确停止。记录每项成功、失败和数据范围，不用凭一段漂亮演示声称“万能”。

## 6. 决策顺序与停止条件

1. **先确认这份“已定/待定/撤回”分类与用户此前意图一致**；不再将助手建议转成用户承诺。
2. **再选择可合法演示的真实异质数据任务**；同时核验官方报名入口、组别与第一次提交性质。不要求产品必须锁定财务+问卷。
3. **做最小可行性实测，而不是完整开发**：模型对两类文件的口径识别/计划、工具返回后的重规划；PDF/RAG 以真实材料衡量价值；多服务切换以可靠性衡量价值。
4. **最后重写 PRD**：只把经论证的体验/功能列为 P0，其余保留条件性扩展；将比赛硬条件写进验收与材料清单，再谈技术架构和开发排期。

**停止条件**：拿不到有权使用的真实数据、模型/工具无法可靠完成分析、无法解释问题口径、数据/密钥隐私不可控或提交要求尚有关键歧义时，不得在 PRD 中将相应能力标为“已验证”或对外宣传。
