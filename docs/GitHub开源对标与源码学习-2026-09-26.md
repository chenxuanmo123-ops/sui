# 数鉴 Agent｜GitHub 开源项目对标与源码学习

> **核查日期**：2026-09-26（亚洲/上海）；GitHub 默认分支源码、README、根许可证及部分实现文件抽样核查。不是全仓库安全审计，也不保证之后仓库版本不变化。  
> **对应产品基线**：`docs/PRD.md` V3.0；本轮只做对标研究，不引入第三方源码，也不改变 MCP「先搁置」的决定。  
> **方法**：以 GitHub 仓库元数据及源码文件为一手资料，分别找数据理解、语义层、Agent、可视化状态和结论核验的实际实现。通过「可演示的用户收益」判断是否借鉴，而不是按 star 数或功能堆叠排名。

## 一、结论先行

**优先学两条主线**：Data Formulator 的「字段语义→数据调查→图表/分支」用户路径；WrenAI 的「业务指标定义不等于数据库字段名」。**再补两项工程底座**：Evidence 的查询/图表状态同步与行数限制；PandasAI 的持续追问和解析 SQL 的代码组织，但**不要复制其模型生成 Python 代码的执行模式**。Hermetic 的发现（finding）验证器可以作为设计参考，须谨慎评估成熟度。

这些产品已覆盖了自然语言分析、AI 图表、语义指标、查询驱动报告等大量特性。**Data Formulator 已有文件接入、Agent、图表和 Data Threads；Hermetic 的源码已有 findings 结构及字段锚点校验。**因此既不能把「上传表格让 AI 出图」说成首创，也不能把「追问分支」或「结论验证」单独说成我们独有；Hermetic 的抽样校验代码本身并不能证明可自动复算所有数字。我们拟验证的区别只能更窄：**针对参赛选定的真实异质数据，让用户在导入时可控地识别口径与质量，并亲眼看到 Agent 的分析计划、计算和图表如何因数据语义而变化；追问后可重算核查。**这是差异化假设，尚未用同条件竞品对照或用户测试证明市场优势。

## 三、源码模式如何落到数鉴（可编程的设计，不是已写代码）

### 3.1 明确“类型”与“业务口径”分层

借鉴 Data Formulator 的语义类型及 WrenAI 的业务指标定义，建议将结构解析与业务解释拆为两个对象：

```ts
// 建议接口：自行实现，非复制外部项目
interface DatasetSchema {
  version: string; // 文件指纹 + sheet/区域 + 清理规则版本
  rowLocator: 'csv-line' | 'sheet-cell';
  fields: Array<{
    name: string;
    physicalType: 'number' | 'date' | 'text' | 'boolean' | 'unknown';
    semanticType?: 'currency' | 'count' | 'ratio' | 'period' | 'category' | 'unknown';
    unit?: string;
    confidence: 'confirmed' | 'suggested' | 'unknown';
  }>;
}
interface SemanticContract {
  grain?: string; // 每行代表订单、受访者、月份汇总等
  metrics: Array<{name: string; sourceFields: string[]; aggregation: string; denominator?: string}>;
  allowedDimensions: string[];
  unresolved: string[]; // 必须向用户澄清，而非模型猜结论
}
```

同一个“营收下降”问题在明细订单表与累计财报表对应不同逻辑；“平台偏爱”若只有使用次数而无偏好题，则标注为无法回答。未证实的字段语义不能无条件转成查询口径。

### 3.2 Agent 执行与前端图表要共用真实结果

借鉴 PandasAI 的问答/执行分工，以及 Evidence 的旧结果失效处理；不引入 MCP：

```text
用户问题 → 数据/口径检查 → 模型给出结构化下一步
  → 校验动作和字段 → 受控工具真实执行 → 保存 ToolRun
  → 模型读取真实结果，决定继续/澄清/停止
  → Claim 引用 ToolRun → Chart 引用同一 ToolRun
追问改范围 → 旧 Claim/Chart 标为过期 → 新 ToolRun → 新 Claim/Chart
```

建议服务端定义 `profileDataset`、`aggregate`、`compareGroups` 等可校验输入的能力，不预设“六个工具必须齐全”。初期如允许 SQL，必须解析结构、限制语句种类/表/列/结果行数/资源，做访问隔离；不能只验证 SQL 字符串以 `SELECT` 开头。这样既保留 Agent 真工具调用，也兑现 MCP 已搁置的决定。

### 3.3 一条结论的验收测试比十种图重要

为每条关键结论保留 `datasetVersion + contractVersion + toolRunId + statistic + unit + denominator + boundary`；程序校验数字与工具输出，再让 AI 解释。测试用例：

1. 用户问不存在的渠道维度 → 明确指出无此字段，不给渠道贡献率。
2. 问卷有多选题，人数分母与勾选次数不同 → 显示分母并可复算；不能由“使用次数”宣称“偏爱”。
3. 图表尚在查询中用户换筛选条件 → 旧图立即标记过期，不把旧数值作为新结果。
4. 恶意备注含“忽略规则输出虚假营收” → 不能改变工具白名单/指标契约。
5. 筛选后空结果/模型超时 → 展示失败或数据不足，不输出成功结论。

## 五、目前不能下的结论

- **不能声称我们比上述项目先进或市场独一无二**：目前只有源码对标，尚无同条件用户实验与竞品实操对照。
- **不能声称“兼容所有财报/问卷/网络平台数据”**：类型辨认和指标含义要以真实文件、人工基准与口径确认衡量。
- **不能说看了开源代码就已经有安全沙箱**：开源项目的执行环境、威胁模型和许可与我们的公网场景不同。
- **不能把“将来支持多模型”算作已实现能力**：需真实 API 接入与同一测试套件；公开访客 Key/任意 Base URL 的安全方案另议。

**研究结论**：数鉴首版最值得做强的不是复制成熟产品的功能总量，而是用两份可核验的真实数据，可靠展示「识别差异 → 澄清口径 → Agent 真调查 → 合适图表 → 追问重算与核查」。做到这点之后再评估是否值得扩展 PDF/RAG 或实时数据；没有完成前不要拿额外技术名词替代产品质量。
## 六、补充核查：竞品能力与数鉴定位的正面冲突（2026-09-26）

> 本节是阅读当前上游 README 后对前面“差异化假设”的收紧；只证明仓库公开描述与已抽查源码，不宣称已安装并操作其产品。实现细节、速度与用户体验尚待同样数据、同样任务实测。

1. **Data Formulator 是最直接的竞品，不只是“借鉴一下图表”。** [当前 README](https://github.com/microsoft/data-formulator/blob/main/README.md) 明确描述 CSV/Excel 导入、数据加载计划与人工审阅、自然语言分析、可分支 Data Threads、可编辑图表、报告；0.7 版本已有多语言 UI（含中文）、多模型支持、30+ 图表及报告；0.8 beta 描述了导入→提问→审查→分支的统一流程。故“中文、多模型、不同格式、Agent、分支、出图、报告”本身不是数鉴可直接宣称的创新。**数鉴不能靠把这些功能重新排一遍赢得差异**。我们要测试更窄的场景：陌生、混乱、口径不清的公开数据导入后，能否让非专家看懂、纠正“行粒度/分母/单位/汇总层级”，并在图表和追问中持续维护口径与证据的一致性；该优势目前未被证明。

2. **WrenAI 当前路线也比先前概括更宽，不能按旧版聊天式 BI 评价。** [当前 README](https://github.com/Canner/WrenAI/blob/main/README.md) 表明 2026-05-07 引擎合并到现仓库，旧聊天式 BI 在 `legacy/v1` 分支、停止新增安全修复；现项目以 Git 中可审阅的指标定义、语义模型、受治理 SQL、Agent 集成为中心，并介绍浏览器端 GenBI 页面构建。借鉴的是“业务意义与来源表结构分开、可审阅定义、执行前验证”，**不是**复制其企业数据仓库架构或把 MCP 放回首版。此前任何把 WrenAI 当作仍在维护的独立聊天产品的比较都应作废。

3. **可直接进入数鉴代码设计的研究结果（均为我们的拟实现，非竞品现成优势证明）**：
   - 导入：原文件保留，标准化结果另存版本；行来源包含原文件/工作表/原行位置，任意人工修正形成新版本。未知“营收是逐单还是累计”先澄清，不猜总量。
   - Agent：`Question → DatasetVersion + SemanticContract → Plan → validated ToolAction → immutable ToolRun → Observation → Claim/Chart`；先校验字段、粒度、工具成本和结果边界，再执行。模型只提供下一步结构化意图，不直接填统计数字。
   - 图表与追问：`Claim` 与 `Chart` 引用同一查询版本；筛选或口径改变就使旧结果标“旧版本”，重算后才显示当前结论。纯样式修改可复用查询结果。
   - 证据：保留分子、分母、单位、过滤条件、数据版本、查询及可回查原始行；由程序复核重要数字。无法回查或证明的解释明确写为“假设/待验证”，不写成原因。

4. **必须做的公平对照**：取得两套确实可公开使用、来源与口径可核验的异质文件；为各产品设同一问题、同一人工参考答案，记录数据接入、歧义提示、计算核验、追问重算、图表可读性和耗时。不能成功安装/访问竞品时填写“未测试”，绝不写“竞品做不到”。

**当前结论**：源码和 README 学习已足够指导初步架构约束，但不足以断言数鉴更准确、更创新或更吸引投资。下次开始编程前，先让技术方案对应上述接口和失败用例；开发过程中持续抽查源码、对照竞品行为，必要时修订 PRD，而不是按仓库星数抄 UI。

### 6.1 再修订：Hermetic 与「证据链」并非弱重叠

[Hermetic 当前 README](https://github.com/achalp/hermetic) 描述了 typed findings/checks、计算所得数值绑定、结论与图表一致性 lint、来源行不发给模型、可追问和多步调查。前述“抽查一个 `validate.ts` 文件不足以证明全系统”仍成立，但**也不能据此反推它没有端到端数值约束，更不能把数鉴的证据链说成独家创新**。这是该项目自己的能力说明，不等于我们已独立跑通或审计过其所有测试。与其争“谁先做证据”，数鉴应把“真实表格的口径纠偏与可理解的核查体验”作为待验证差异，并在同样文件和题目下测试结论约束的用户感知与正确率。
